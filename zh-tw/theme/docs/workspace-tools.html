Workspace tools: the contract

The pull workspace (~/jbisfun) runs four Zig programs. Each one lives in its own repo and is its own pull job, with its own web server, CLI and MCP server. They share this package and reach each other over HTTP/JSON only.

tool repo job label default listen does
cpull cpull cpull 127.0.0.1:8080 forge: repos, issues (incl. anchored reports), patches, stacks, the merge gate, commit links
idlci idlci idlci 127.0.0.1:8737 CI: idl projects, job queue, runners, logs, patch/stack runs
wiki wiki wiki 127.0.0.1:8090 the static site generator (wiki build/publish) and its live server
radar radar radar 127.0.0.1:8746 capturing and tracking line-anchored reports. The reports are stored as cpull issues

Nothing links another tool’s code. The shared pieces live in this package (jbisfun/theme), which every tool takes as a sibling path dependency:

// build.zig.zon
.theme = .{ .path = "../theme" },
// build.zig
const theme_dep = b.dependency("theme", .{ .target = target, .optimize = optimize, .highlight = true });
mod.addImport("theme", theme_dep.module("theme"));
mod.addImport("discovery", theme_dep.module("discovery"));
mod.addImport("highlight", theme_dep.module("highlight")); // only with .highlight = true

../theme is the workspace checkout at ~/jbisfun/theme. Any tool built outside the workspace needs that checkout beside it. .highlight defaults to false for dependents, and the tree-sitter grammars are lazy dependencies, so a tool that doesn’t highlight never fetches them. Asking for module("highlight") without .highlight = true panics at configure time. Who highlights: cpull (file view), wiki (code blocks) and radar (excerpts, optional). idlci doesn’t.

1. Finding each other: .pull/<tool>/

  • Root. A tool finds the workspace from --root DIR, else $PULL_ROOT, else the nearest ancestor of the cwd that holds pullfile.plist. pull jobs run from the root with the workspace env.
  • State. Everything a tool keeps goes under <root>/.pull/<tool>/: .pull/cpull, .pull/idlci, .pull/wiki, .pull/radar. idlci keeps idlci’s existing .pull/idlci/idlci.db. The CI port inside cpull migrated it into .pull/cpull/ci/ci.db, and phase 2 moves that file back, along with logs/ and work/.
  • Serving. After binding its socket, a server calls discovery.announce(io, gpa, root, tool, addr). That takes an exclusive lock on .pull/<tool>/serve.lock for the life of the process (error.AlreadyServing if another server holds it) and writes .pull/<tool>/serve.addr = the bound host:port, with no scheme and no newline. On a clean stop the server calls Serving.release. A crash leaves serve.addr behind, but the kernel drops the lock, so readers treat it as stale.
  • Reading. discovery.read(io, a, root, tool) returns the address while a server holds the lock (or when there is no serve.lock at all), otherwise null. Clients pick the address with discovery.connectAddr(io, a, root, tool, explicit): the --addr flag or env var (CPULL_ADDR, IDLCI_ADDR, WIKI_ADDR, RADAR_ADDR) first, then serve.addr, then the default port.
  • Health. Every server answers GET /api/health with {"ok":true,"tool":"<tool>","root":"<abs root>","version":"..."}. A client must check that root is its own workspace before trusting an address. cpull’s cpull ci already does this.
  • cpull currently writes .pull/cpull/serve.addr itself (src/ci/app.zig) and locks .pull/cpull/ci/serve.lock. Phase 2 switches it to announce(.cpull).

2. The shared global bar

Every tool page extends theme/layout.html and sets Layout.tools = try theme.workspaceTools(io, arena, root, .<self>, &.{}). The bar lists Forge · CI · Wiki · Radar right after the brand. The current tool is highlighted. A tool that is running links to http://<its serve.addr>/. A tool that isn’t running is dimmed and has no link. Discovery runs once per page render (two small file reads and a lock probe per tool). The tool’s own items (Layout.nav) follow after an etched divider.

  • mounted overrides entries. Pass .{ .tool = .idlci, .base = "/ci" } while a tool is still served in-process; cpull does this for /ci and /wiki/ until phase 2.
  • The wiki’s own templates (wiki/templates/partials/navbar.html) call the same macro: {% import "theme/macros.html" as ui %}{{ ui.tools(tools) }}. The live server passes tools. The static dist/ that wiki publish produces passes an empty list, so the published site shows no tool bar.
  • Links between tools are absolute (http://127.0.0.1:8737/jobs/42). A JSON API that returns a link returns a path on its own server (/jobs/42, /<identity>/issues/<id>), and the caller prefixes the base URL it used to reach that server. Pages that show another tool’s links do the prefixing.

3. Conventions for every JSON API

  • JSON in and out (content-type: application/json). Errors are {"error":"message"} with a 4xx/5xx status. Ids are cpull’s 32-hex event ids, and any unique prefix of at least 6 hex digits is accepted where an id is input.
  • No CORS. Browser pages never call another tool directly. A tool’s own page script calls its own server, and that server calls the other tool (the wiki proxies, see §6).
  • Writes are POST. A server rejects a request whose Origin header names a different origin (403), so another site can’t drive it. Server-to-server calls send no Origin.
  • The servers bind 127.0.0.1 and have no accounts. Every forge write is made by cpull and authored as pull’s identity, which pull cpull open pins per repo. The other tools never write events themselves; they ask cpull.
  • repo is a pullfile repo name (group/name for nested ones). . (or "") is the workspace’s events repo, which is pullfile cpull.events, dotenv here.

4. cpull (127.0.0.1:8080, /api)

These routes are new in phase 2. They expose what src/integrate/forge.zig, src/report/report.zig, src/wiki/forge.zig and cpull records do in-process today. HTML pages and form routes stay as they are.

GET  /api/health
GET  /api/repos                         -> [Repo]
GET  /api/issues?repo=R&status=open|closed|all&label=L&anchored=1&file=F
                                        -> [Issue]        (default status=open; repo omitted = every repo)
GET  /api/issues/<repo>/<id>            -> Issue + "comments": [Comment]
POST /api/issues                        {repo, title, description, labels?, anchor?}  -> 201 Issue
POST /api/issues/<repo>/<id>/comment    {body, status?: "open"|"closed"}               -> Issue
POST /api/issues/<repo>/<id>/close      {comment?}                                     -> Issue
POST /api/issues/<repo>/<id>/reopen     {comment?}                                     -> Issue
GET  /api/reports?status=open|closed|all&repo=R&file=F     -> [Report]    (issues labelled `report` with an anchor)
GET  /api/reports/<id>                  -> Report + "excerpt": Excerpt|null
GET  /api/patches?repo=R                -> [Patch]
GET  /api/patches/<repo>/<id>           -> Patch
GET  /api/stacks/<id>                   -> Stack
GET  /api/records?repo=R[&repo=R2...]   -> exactly `cpull records PATH...`'s JSON, for those repos
  • Repo = {name, identity, path, branch, url, issues_url, cloned, open_issues, open_reports}. url/issues_url are cpull page paths. These are the wiki forge’s RepoInfo fields plus identity, path and branch (the pullfile branch).
  • Issue = {id, repo, title, description, labels, status, author, created, url, anchor?}. labels is the space-separated string the event carries. created is RFC 3339 UTC. anchor = {file, line, line_text, quote?, commit?, source?} exactly as in the event (docs/report.md in cpull), and is present only when set.
  • Comment = {id, parent_id, body, author, created}.
  • Report = the object cpull report list --json prints today: {id, repo, file, line, line_text, quote, note, title, status, source, commit, created, author, url}.
  • Excerpt = cpull report/anchor.zig Excerpt: {file, line, filed_line, first, lines, commit, at_filed_commit, changed}.
  • Patch = {id, repo, title, description, status, source_branch, tip, url}. source_branch is null for a patch from a fork. tip is the source branch’s current oid, or null.
  • Stack = {id, title, description, status, url, members: [{repo, patch_id, branch, oid}]}. Only members whose source branch exists are listed (patchci.stackMembers).
  • POST /api/issues with an anchor stores it verbatim. The caller (radar) has already read line_text and commit. cpull adds the report label when an anchor is given.

cpull keeps in-process: anchored issue pages and excerpts, file-view report flags and its “report this line” form (/<repo>/report), #id links, the fixes #id scanner, and the merge gate. Phase 2 moves the scanner’s link_tips and the CI issue maps (ci_issues, issue_jobs) out of the CI db into cpull’s own state file, .pull/cpull/integrate.json: {"link_tips":{repo:oid}, "ci_issues":{key:{repo,issue}}, "issue_jobs":{"repo issue":[job ids]}, "ci_cursor":"..."}.

5. idlci (127.0.0.1:8737, /api)

These are today’s /ci/api routes, served at the root, plus the routes cpull needs for its balls and its CI issues. The JSON shapes are those of cpull src/ci/db.zig and app.zig (Job, Enqueued, ProjectView, LogChunk) and src/integrate/status.zig (Summary, JobRef). Pages move from /ci/... to /....

GET  /api/health
GET  /api/projects                      -> [ProjectView]   (includes git.repo: the pullfile repo holding the project)
GET  /api/projects/<path>               -> ProjectView
GET  /api/jobs?status=&project=&limit=  -> [Job]   newest first
POST /api/jobs                          NewJob -> Enqueued
GET  /api/jobs/<id>                     -> Job
GET  /api/jobs/<id>/log?offset=N | ?tail=N  -> LogChunk {id, status, size, next_offset, text}
GET  /api/jobs/<id>/events              SSE: `log` (id = byte offset), `status`, final `done`
POST /api/jobs/<id>/cancel              -> Job
POST /api/jobs/<id>/retry?by=web|mcp|cli|watch  -> Enqueued
POST /api/runs                          {subject, members:[{repo, patch_id, branch, oid}], requested_by?}
                                        -> {subject, checkout, jobs:[Enqueued]}
GET  /api/status/repos                  -> {"<repo>": Summary|null, ...}   every pullfile repo
GET  /api/status/repo/<repo>            -> Summary|null
GET  /api/status/commits?repo=R         -> {"<oid[0..7]>": Summary}     status.commitIndex
GET  /api/status/subject?subject=S&tips=T -> Summary|null               status.forSubject; T = "<repo> <oid>" lines, url-encoded
GET  /api/feed?cursor=C&wait=S&limit=N  -> {cursor, jobs:[FeedJob]}
  • Runs. POST /api/runs replaces /ci/api/patch and /ci/api/stack (integrate/patchci.zig queue). subject is patch:<repo>:<patch id> or stack:<stack id>, and cpull resolves the members (GET /api/patches|stacks above). idlci picks the idl projects in the member repos, adds the repos their targets live in at the workspace’s current HEADs, and checks it all out in .pull/idlci/work/<subject>/, a pull-style tree of linked worktrees plus a pullfile copy, as ci/work.zig does now. It queues build and test per project, with subject/checkout recorded on each job. idlci patch REPO ID, idlci stack ID and MCP ci_patch/ci_stack resolve the members through cpull’s API and then post here.
  • Balls. Summary = {ball: "passed"|"failed"|"running"|"warning"|"none", label, href, jobs:[JobRef], green, stale}. JobRef = {id, label, status, ball, href, when, head}. href values are idlci paths (/jobs/42, /projects/<p>); cpull prefixes idlci’s base URL. When idlci isn’t running, cpull shows no CI column or group, which is today’s “no CI” path in integrate/view.zig.
  • Gate. cpull keeps cpull.require_ci and the gate’s logic (integrate/gate.zig). It reads GET /api/projects for the repos that have projects and GET /api/status/subject for the stack and member subjects. If idlci is down and the gate is required, cpull refuses to merge, with a “CI not reachable” reason, unless --force.
  • Feed (replaces the runner’s on_finish hook, integrate/ciissue.zig). The feed lists jobs that reached a final status (passed, failed, cancelled) after cursor, oldest first. cursor is opaque (idlci uses "<finished>.<id>"). The first call without a cursor returns the current cursor and no jobs. wait=S (≤60) long-polls until something finishes. FeedJob = Job + {"idl": "idl build -c release", "log_tail": "<last 30 lines, ≤6 KiB>"} (ciissue.describe/tail). cpull polls the feed every few seconds, applies ciissue.zig’s rules (a workspace job, not a subject job, on a repo checked out on its pullfile branch; file, comment, reopen or close the ci issue), and stores ci_cursor. The job links it writes into issues are absolute idlci URLs.
  • pullfile. idlci reads the pullfile itself, for the repo list and branches (repoOf), and keeps require_ci/ci_issues out of its own config (those are cpull’s).

6. wiki (127.0.0.1:8090)

The wiki server serves .pull/wiki/dist. It rebuilds at most every few seconds as pages are requested (today’s src/wiki/serve.zig, at / instead of /wiki/). It injects <meta name="cpull-wiki" content="/_forge"> into served pages only. Its forge features talk to its own server, which proxies:

GET  /api/health
GET  /api/pages?repo=R                  -> {repo, url, docs: [{file, url}]}   (lets cpull/radar link "open in wiki")
GET  /_forge/page?repo=R&file=F         -> today's PageInfo: cpull GET /api/repos + radar GET /api/reports?repo=R&file=F
GET  /_forge/repos                      -> today's [RepoInfo] from cpull GET /api/repos (urls made absolute to cpull)
GET  /_forge/ci/projects                -> idlci GET /api/projects (hrefs made absolute)
POST /_forge/report                     {repo, file, line, quote?, note?, title?} -> radar POST /api/reports (source "wiki")

assets/forge.js and assets/radar.js in the wiki repo change their URLs from /wiki/_cpull/... and /ci/api/projects to these. Any /_forge call whose target tool isn’t running answers 503 {"error":"<tool> isn't running"}, and the scripts already treat failure as “no forge”. wiki build|publish|clean keep today’s cpull wiki ... behaviour. Output moves to .pull/wiki/{dist,build}, $WIKI_TRANSLATE/$WIKI_PUBLISH_DIR/$WIKI_ESBUILD keep their meaning, and the precommit hook becomes wiki publish.

7. radar (127.0.0.1:8746)

radar owns capture and tracking: the CLI, MCP, editor and wiki capture, anchor creation (reading line_text from the work tree, commit = HEAD when HEAD has the same text on that line, as report.zig add does now), relocation, and its own small web UI that lists reports. Reports are stored as cpull issues through cpull’s API.

GET  /api/health
GET  /api/reports?status=open|closed|all&repo=R&file=F  -> [RadarReport]
GET  /api/reports/<id>                  -> RadarReport + "excerpt": Excerpt|null
POST /api/reports                       {repo, file, line, quote?, note?, title?, labels?, source?, ref?} -> 201 RadarReport
POST /api/reports/<id>/close            -> RadarReport
POST /api/reports/<id>/reopen           -> RadarReport
POST /api/relocate                      {repo, file, line, line_text} -> {line|null, changed}
  • RadarReport = cpull’s Report plus {current_line, moved, changed}. current_line is the line holding line_text nearest the filed line in the work tree’s file (report/anchor.zig relocate), or null when it’s gone. changed means the text no longer appears. moved means current_line != line.
  • POST /api/reports builds the anchor (with ref set, the line is read at that commit instead of the work tree, as cpull’s web form does), then calls cpull POST /api/issues with labels + report and the anchor, and returns the new issue as a report. close/reopen go to cpull’s close/reopen. Listing reads cpull GET /api/reports and adds relocation.
  • CLI, compatible with the old Rust radar and cpull report: radar [add] REPO FILE LINE [-q QUOTE] [-n NOTE] [--title T] [--labels L] [--source S], radar list [--all] [--json], radar show|close|reopen ID, radar migrate FILE (the radar.db JSON import from report.zig), radar serve [--listen ADDR], radar mcp. The CLI talks to cpull’s API directly and doesn’t need radar’s own server. If cpull isn’t running, it fails with “cpull isn’t running (start the cpull job)”.
  • ycode-radar (radar.x.lua) and ycode-pull switch from pull cpull report ... to radar .... pull cpull report goes away in phase 2, or becomes a pass-through to radar.

8. MCP

Each tool has <tool> mcp (stdio, parley, as in pull’s pkgs/mcp). It finds the workspace like the CLI does and talks to the servers over HTTP. Registered in the pullfile mcp_servers section (before repos), which pull mcp-servers and ycode-pull read:

<key>mcp_servers</key>
<dict>
	<key>idlci</key>
	<dict>
		<key>args</key>
		<array>
			<string>mcp</string>
		</array>
	</dict>
	<key>radar</key>
	<dict>
		<key>args</key>
		<array>
			<string>mcp</string>
		</array>
	</dict>
	<key>wiki</key>
	<dict>
		<key>args</key>
		<array>
			<string>mcp</string>
		</array>
	</dict>
</dict>
server tools
idlci mcp ci_projects, ci_queue, ci_jobs, ci_job, ci_log, ci_wait, ci_cancel, ci_retry, ci_patch, ci_stack: same names and input schemas as pull’s pkgs/mcp/src/ci.zig today, with the description prefix idlci:
radar mcp radar_report (file), radar_reports (list), radar_report_show, radar_report_close, radar_report_reopen: the schemas of pull’s cpull_report* tools today
wiki mcp wiki_build (incremental build, returns what changed), wiki_pages (a repo’s page and doc urls on the live server)
pull mcp keeps cpull_* for issues, patches and stacks (cpull_issues, cpull_issue, cpull_new_issue, cpull_comment, cpull_close, cpull_reopen, cpull_sync, cpull_patch, cpull_stacks, cpull_stack, cpull_merge). It drops ci_* and cpull_report*. cpull_stack prints the CI and gate from idlci’s /api/status/subject when idlci is running

idlci’s MCP (and the old Rust one) may start the server when it isn’t running only through pull: pull launchctl start idlci, never by spawning a detached server of its own.

9. pull jobs

Each server is a pullfile jobs entry, like cpull’s:

<dict>
	<key>Label</key>
	<string>idlci</string>
	<key>ProgramArguments</key>
	<array>
		<string>idlci</string>
		<string>serve</string>
		<string>--listen</string>
		<string>127.0.0.1:8737</string>
	</array>
	<key>RunAtLoad</key>
	<true/>
	<key>KeepAlive</key>
	<dict>
		<key>SuccessfulExit</key>
		<false/>
	</dict>
</dict>

wiki and radar use wiki serve --listen 127.0.0.1:8090 and radar serve --listen 127.0.0.1:8746. cpull keeps pull cpull open --web-listen 127.0.0.1:8080. In phase 2, cpull drops --ci-jobs, --ci-watch and --ci-watch-interval, which become idlci serve --jobs N --watch [--watch-interval S]. Binaries install to ~/.local/bin (zig build -Doptimize=ReleaseSafe --prefix ~/.local).
