browser-ios

The AOSP Browser (the last full one, Android 6.0.1) re-created for iOS in SwiftUI on WKWebView, in Fossify style.

idl build -c release     # -> build/release/FossifyBrowser.ipa (ad-hoc signed; re-sign to install)
idl install "<device>" FossifyBrowser

Ported: the phone UI (title bar with security/favicon icon, url input, stop/reload, tab count, options menu; page progress bar); url suggestions (typed text, bookmarks, history, the search engine’s suggestions, the “insert” arrow); tabs with the NavScreen tab switcher (cards with title, close and page thumbnail, swipe to close, new tab, close other tabs), 16-tab limit, pop-ups/target=_blank in new tabs, window.close(); incognito tabs (shared non-persistent data store, dropped with the last incognito tab, never saved); bookmarks with folders and breadcrumbs, add/edit/move/delete, folder “open all”, bookmark/history context menus, set as homepage; history grouped by date (Today, Yesterday, Last 7 days, Last month, Older) plus Most visited, star toggle, clear; the Most visited homepage with thumbnails; find on page with match count; share page; save for offline reading (Saved pages, .webarchive); downloads (WKDownload, save link, save image) into Documents/Download with a downloads list; request desktop site per tab; page info with certificate; long-press menus for links (open, open in new/background tab, save link, copy, share), images (save, view, copy URL, share), tel: and mailto:; JavaScript alert/confirm/prompt, HTTP authentication, the SSL warning dialog; location (per-site prompt with “Remember preference”), camera and microphone prompts; tabs (with back/forward lists), bookmarks, history, favicons and thumbnails persisted as JSON/JPEG; BrowserRoot(openURL:) opens a page or a local .html/.webarchive. Settings: homepage (current, blank, default, most visited, other), privacy & security (clear cache/history/cookies/all site data, security warnings, accept cookies, enable location, clear location access), accessibility (force enable zoom, text scaling, minimum font size, inverted rendering + contrast, with previews), advanced (search engine, search suggestions, open in background, JavaScript, website settings, block pop-ups, desktop sites, reset to default), bandwidth (load images).

Differences forced by iOS: pages are drawn by WebKit, not Chromium (see below); form auto-fill and saved passwords belong to iOS AutoFill, so their settings are gone; plug-ins, text encoding, default zoom, overview mode, preloading, quick controls and home-screen shortcuts have no WKWebView/iOS equivalent; geolocation goes through an injected navigator.geolocation shim because WKWebView has no public per-site location callback; text scaling, force zoom and inverted rendering are injected CSS, image and cookie blocking are content rule lists; the search engine list is today’s engines; the app can’t be the system default browser.

Chromium

All browser code talks to BrowserEngine/BrowserPage (Sources/Engine/BrowserEngine.swift); WebKitEngine is the only implementation, picked in Engines.current. A Blink engine would be a second implementation of those two protocols. Findings (no build attempted):

  • BrowserEngineKit (iOS 17.4+) is the only way to run a non-WebKit engine: the host app needs com.apple.developer.web-browser-engine.host plus three arm64e extension processes with .webcontent (JIT optional), .networking and .rendering, and the default-browser entitlement (or the embedded-engine entitlements for in-app browsing). Apple grants them per app on request, for distribution in the EU (iOS 17.4+) and Japan (iOS 26.2+) only; development builds run on devices in those regions only.
  • The darwin SDK here (~/.swiftpm/swift-sdks/darwin.artifactbundle, iPhoneOS 27.2) ships BrowserEngineKit and BrowserEngineCore (headers, .tbd, swiftinterface: BEWebContentProcess, BENetworkingProcess, BERenderingProcess, BELayerHierarchy, BEScrollView, BETextInput, …), and idl builds appex targets, so the host/extension skeleton would compile on Linux.
  • Chromium’s iOS Blink port is GN use_blink = true (targets content_shell, chrome), “experimental, only for analysis” upstream. Building it needs a Mac with Xcode 26+ and the iOS simulator runtime (ios/build/tools/setup-gn.py); it doesn’t build on Linux.
  • Jimpactor sideloading signs with free/paid development certificates whose profiles can’t carry the web-browser-engine entitlements (managed, granted only to an approved App ID), and iOS refuses to launch binaries claiming restricted entitlements their profile lacks. Blink also can’t run inside one plain app process on iOS (no JIT, no child processes), so there is no entitlement-free fallback.
  • Bottom line: replacing WKWebView needs an Apple-approved EU/JP browser entitlement profile and a macOS Chromium build; until then WebKit is the only engine this app can ship.

GPL-3.0 like the other Fossify ports; the AOSP Browser it follows is Apache-2.0.
